## Overall response

I agree with the proposal's main direction: establish a small, single-agent baseline, match the actual model and reasoning effort before comparing harnesses, reduce unnecessary model/tool cycles, and measure time to a correct, verified result. The distinction between mechanism tests and demonstrated performance is important. The offline results in the proposal do not establish that this setup matches Codex in latency, token consumption, or research quality.

My goal is to make the existing setup more efficient while retaining the useful parts of our earlier research. Those include evidence provenance, durable project notes, scoped read-only reviewers, explicit permission boundaries, and reversible context management. These should be available when the task benefits from them, rather than automatically imposing a planning, delegation, and review pipeline on every small edit.

## Useful prior research to retain

The earlier lab notes support a small set of durable practices:

- Keep conclusions in project files; a child-agent session is not a durable knowledge store.
- Prefer native, on-demand skills and narrow agents over importing a large extension catalog.
- Record source URLs, access dates, revisions, supported claims, and uncertainty.
- Treat external pages, repository documents, and tool output as evidence, not instructions.
- Delegate only substantial independent questions, with a bounded objective and stopping condition.
- Use deterministic verification when available; use independent review where it adds coverage.
- Evaluate pruning for evidence loss and reversibility, rather than assuming a smaller context is always better.
- Keep extension provenance and a practical removal/rollback path.

These are compatible with the proposed baseline. The research assets can remain available for normal research work while the isolated benchmark excludes them as required. Native skills are loaded on demand, but discovery metadata and agent definitions may still contribute overhead; their cost should be measured rather than declared zero.

Earlier research references: `~/Code/AI_blog/articles/opencode_lab/research/README.md`, `research/notes/official-docs.md`, `research/notes/community-patterns.md`, and `research/sources.md`. That ledger records access on 3 October 2026; volatile behavior still needs checking against the installed version. The newer proposal has its own source list dated 9 October 2026. ## Recommended adaptation of the proposal

### 1. Inventory before choosing configuration syntax or model defaults

Capture the installed version, locked package version, supported CLI flags, resolved configuration, active instruction files, selected model/variant, provider route, and active integrations. Inspect metadata without including credentials. In particular, do not substitute an invented model ID or assume that V1 and V2 configuration fields can be mixed on our installed release.

The current module is already wired into a broader Nix configuration with local changes. Preserve that starting state and use a disposable worktree or fixture for configuration experiments. A package supplied by locked Nix inputs is reproducible relative to those inputs, but the exact resulting OpenCode version still needs to be recorded.

### 2. Separate the measured baseline from normal research use

Create an isolated baseline that excludes optional plugins and inherited integrations, uses the native provider route, and runs one agent at the same model and effort as the comparison. Verify isolation from the effective configuration; an empty project plugin or MCP entry alone is not sufficient evidence.

Preserve the existing research skills, restricted reviewers, and planning material for normal work. After establishing the baseline, reintroduce optional capabilities one at a time. Compare their effect on correctness, total usage, elapsed time, and evidence retention. This avoids confusing a convenient everyday setup with a controlled benchmark arm.

Superpowers is a particularly useful variable to inspect because workflow requirements can add planning and approval stages even to small tasks. Planning hooks and DCP may also affect prompt construction or session behavior. These are plausible mechanisms to investigate, not measured diagnoses of this configuration.

### 3. Keep instructions concise and task-specific

Use short project instructions covering the deliverable, acceptance criterion, targeted reads, independent read batching, dependent operation ordering, and stopping condition. Preserve indispensable research conventions and compute limits. Load long method guides when needed instead of making them universal instructions.

For routine work, one agent should be the default. Explicit research/review/verify commands remain useful when their independent coverage justifies another session. Avoid requiring all three for every change.

### 4. Treat reasoning and output management as separate variables

First match effort to the reference harness. Then test lower effort on routine tasks while preserving stronger reasoning for difficult mathematical or conceptual work. `economy`, `balanced`, and `deep` variants are a reasonable later interface, once the exact model and supported configuration shape are known.

Keep full logs recoverable and return targeted diagnostics or compact summaries. The existing 32 KiB cap is not equivalent to the proposal's suggested token range. Do not tighten it solely to meet an arbitrary budget: check that failures, stderr, mathematical conventions, seeds, and result paths survive. Batch independent reads and avoid repetitive polling of unchanged logs.

### 5. Evaluate context management independently

Start with automatic native compaction in the baseline and test pruning separately. For normal research sessions, preserve exact result paths, conventions, failed approaches, decisions, and unresolved questions in files.

The DCP configuration expresses a cautious policy, but some details deserve specific validation: manual mode disables automatic strategies while individual strategy flags remain enabled, and `protectUserMessages` is false. These are observations of the configuration, not evidence that user requirements or error diagnostics have actually been lost. Test behavior on a reversible fixture before retaining or changing those choices.

### 6. Measure before claiming an improvement

Use identical disposable starting states, matched model/effort, fixed prompts, and external acceptance checks. Include failed attempts and child/auxiliary usage where exposed. Preserve raw usage and label unavailable fields as unknown. Record approval delays separately so that model latency and human interaction are not conflated.

Begin with a small instrumentation pilot, then use the proposal's paired task suite. Investigate persistent-server operation only if startup is material, and cache/transport changes only if traces show a remaining issue. No live benchmark or validated speedup is established by this response.

## Requested implementation outcome

The eventual change should produce an efficient default workflow and a verifiably isolated benchmark baseline, while retaining the research assets that improve correctness. It should preserve existing permission boundaries, identify the exact installed configuration dialect, record how to opt into optional workflows, and provide clear validation and rollback instructions. The current configuration below supplies the concrete starting point that the original proposal lacked.
